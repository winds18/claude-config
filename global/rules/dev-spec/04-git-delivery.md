# Git 与交付

## Git

- 沿用项目的分支、提交与发布约定。无约定时：短命工作分支，小而完整的提交，Conventional Commits（`feat|fix|refactor|docs|test|chore|perf|ci: 描述`）。
- 提交前检查真实暂存 diff，只含同一目的的改动，并运行该改动所需的检查；不提交密钥、构建产物、临时文件。
- 推送前核对目标分支与将发送的历史。不改写他人提交，不对共享分支强推，不借"清理"删除他人文件。
- 在默认分支上需要提交时先建分支。提交、推送、PR、合并、发布是不同动作，各自按授权执行；"可以提交"不等于"可以推送"。用户在 CLAUDE.md 里给了长期授权的动作按其范围直接进行。
- 例外：并行开发所需的本地检查点提交（任务分支上的契约检查点、worktree 子代理分支上的提交）属于并行流程本身，可直接进行；合入默认分支与推送仍需授权。用户禁止提交时不做并行写，改为串行。
- 同步基线分支：宿主提供工具（如桌面端 `sync_with_base_branch`）时优先使用，否则自己 merge 并解决冲突。并行分支之间的集成冲突按 `parallel-dev` 处理。

## 文档与版本（随阶段递进，不过度文档化）

| 阶段 | 文档 | 版本 |
| --- | --- | --- |
| 原型 / 主体功能未跑通 | README 只写怎么跑起来；关键决定写进提交信息 | 不打版本 |
| 主体稳定（接口基本定型或已有使用者） | 接口变化只同步受影响的段落 | SemVer；发布说明由 Conventional Commits 生成，不手写 CHANGELOG |
| 正式发布 | 仅破坏性变更附升级/回滚说明 | tag 只打在 CI 通过的提交上 |

- 只写代码、类型、测试表达不了的事实；同一事实只写一处；能生成的不手写。项目已有约定时从其约定。

## PR 与 CI

- 发 PR、读 CI、处理 CI 失败与范围外问题的做法见 `dev-workflow` 技能 §7。推送到已有 PR 前先看标签：带 PR Steward 标签说明另有代理在管理，不推送，先请用户选择；本机没有 `gh` 看不了标签时，向用户确认后再推。

## 完成条件

只有同时满足才报告完成：

1. 请求范围全部实现，架构、契约与所有消费者一致；
2. 必要验收在**当前集成状态**上通过（列出命令/操作与结果）；
3. 无未处理的明显复杂度退化或结构复杂化，性能约束有证据；
4. 自有临时文件、无关进程、后台代理已清理或说明保留理由。

未满足的项明确写成"未完成/阻塞/未验证"，附具体原因。不把"已派发""子代理说通过""应该可以"当作完成。

## 交付说明格式

- 改了什么（按用户可观察行为描述，附关键文件链接）；
- 怎么验证的（命令与结果，失败也如实给出）；
- 取舍与已知限制、需要用户决定的事项。
