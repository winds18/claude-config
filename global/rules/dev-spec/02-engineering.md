# 工程约定

## 流程

- 跨模块功能、重构或多阶段工作按 **需求与验收 → 架构与模块边界 → 接口契约 → 并行实现 → 集成验证** 推进，细则调用 `dev-workflow` 技能。已有架构和契约适用时直接复用，技术决定不逐阶段报批。
- 方案存在多个合理方向且选错代价高时，先进入 Plan 模式出方案再动手；小修直接改。
- 依赖同一契约的实现必须等契约稳定后再并行；契约以项目现有权威形式（类型、schema、OpenAPI、proto）表达，不手抄第二份定义。

## 质量底线

- 正确性、边界与失败恢复是前提；执行效率和可维护性同样是交付要求。
- 按真实规模选算法和数据结构，关键路径说清时间/空间复杂度与 I/O；关注 N+1、重复扫描、无界内存/并发。性能结论要有可复现测量，不凭直觉加缓存或并发。
- 职责集中、命名准确、依赖可追踪；减少重复、隐式状态和无依据的抽象。只在本次改动边界内整理，不借机重写无关代码。

## 测试与验证

- 按行为与风险选择检查：缺陷修复先复现旧失败再修；接口变化验证真实生产者与消费者，不能只有两套同假设的 mock；UI 改动做真实渲染检查（`/run`、浏览器或模拟器）。
- 不得删测试、弱化断言、跳过错误或缩减需求来制造通过。失败先区分实现、环境、测试本身三类原因；修改测试须说明与需求的冲突并保留等效或更强的验证。
- 证据只对当时验证的文件与环境有效；共享接口或依赖变化后重跑受影响检查。未验证的部分明确标为未验证。

## 目录与临时文件

- 沿用项目现有布局；新项目只建实际需要的目录，不预建空目录或空抽象层。
- 一次性文件放会话 scratchpad 或系统临时目录；必须留在项目内时用任务独占的 `.tmp/<task>/`，用 trap / try-finally 安排清理。
- 只清理本任务创建的路径和进程；gitignore 不等于已清理。需要保留的证据放约定的产物目录并说明用途。
