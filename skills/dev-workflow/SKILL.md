# 工程流程

按依赖顺序推进；改动范围决定设计深度。现有架构、契约和项目流程足够时直接复用，只补实际变化。各阶段由你依据已有授权做技术判断，不逐阶段等用户批准。

## 1. 需求与验收

- 写清用户可观察结果、范围、必须保持的兼容性、验收场景；从代码和现有检查确认基线（先跑一次现有测试，记录既有失败）。
- 涉及规模或性能时，明确代表性数据量、增长预期与指标（延迟/吞吐/内存/外部调用次数）。缺少指标时写出合理假设，不编造统一门槛。
- 影响产品行为的实质歧义才提问；方向多且选错代价高时用 Plan 模式出方案。

## 2. 架构与模块边界

- 先读现有入口、依赖与数据流，决定改动落在哪些模块、各自职责与允许的依赖方向；避免循环依赖、跨层直连、为并行另造框架。
- 只处理相关风险：数据归属与生命周期、外部依赖、权限/信任边界、失败恢复、持久化迁移与回退。
- 产出是足以指导实现的边界决定（已有模块说明、简图或短 ADR 均可），不是一堆空目录。

## 3. 接口契约

- 在依赖方开工前确定：输入/输出、类型与约束、错误语义、状态变化、兼容要求；跨服务再补鉴权、超时、重试/幂等。
- 用项目已有权威形式（语言类型、schema、OpenAPI、protobuf），文档只引用不复制。给出能消除歧义的成功/失败示例，必要时写契约测试固定行为。
- 契约只有一个负责人。修改契约时同步所有消费者与相关测试；并行前把契约提交为 git 检查点（见 `parallel-dev`）。

## 4. 并行实现

- 按模块/文件与运行资源切工作包（各包 `owned` 不重叠、共享文件进 `forbidden`），调用 `parallel-dev` 技能：`/dev-spec-dispatch` 准备并生成提示，按三阶段派发，`integrate.py` 集成。
- 只有一个包或强依赖时不并行，主会话直接实现。
- **对抗用例先行**（L 档必做，M 档建议）：动手前先列出会让实现出错的具体场景并写成测试——并行时 `dispatch.py prompts` 为每个包生成 `case-designer` 的提示；串行实现时自己派一个 `case-designer` 子代理。清单覆盖输入边界、失败路径、外部状态残留、同名/改名、兼容与规模，只保留与本次改动相关的条目；数量与规模相称，机械性的包不做。依据：事后复核发现的问题大多可以事先列举（见 docs/incidents.md）。
- 先打通最小真实主路径，再补错误处理和边界。Mock/占位必须遵循已定契约，不能冒充真实集成。

### 实现质量与效率

| 维度 | 要求 |
| --- | --- |
| 算法与数据结构 | 按输入规模、分布、访问模式比较方案；关键路径说明复杂度与取舍。选择不明时查权威资料、比较成熟实现或做小原型，优先标准库/成熟库 |
| 实际开销 | 排查重复扫描、N+1、重复 I/O、多余拷贝、无界内存/并发；索引、批处理、流式、并发按瓶颈采用；新增缓存须处理一致性与失效 |
| 结构清晰 | 函数与模块职责集中，命名反映业务语义，数据流可追踪；避免混杂业务与基础设施的大函数、散落重复、隐式全局状态、层层特判 |
| 克制抽象 | 复用稳定共性，保留有意义的差异；抽象必须降低理解与修改成本；不追求最少行数或炫技写法；性能所需的复杂实现留一句取舍说明 |
| 有证据的优化 | 影响复杂度/资源或有性能目标时：建立可复现基线 → 定位瓶颈 → 比较方案 → 记录输入、环境、命令、指标；覆盖大规模/最坏分布，正确性检查不减 |

普通局部修改只需检查复杂度与开销，无需搭基准平台。

## 5. 测试与集成

| 变化类型 | 至少要证明 |
| --- | --- |
| 业务逻辑 / 缺陷修复 | 规则、边界与原失败场景；能复现时先确认旧实现失败，再加回归测试 |
| 模块 / 接口 / 数据格式 | 生产者与消费者真实连接兼容、输入约束、错误语义 |
| 存储、迁移、有副作用操作 | 约束、失败恢复与重复执行（幂等）；用隔离数据，不碰真实用户数据 |
| 用户主流程 / 关键 UI | 受影响关键路径的集成或端到端验证，含失败状态；界面改动按 `ui-quality` 技能验证（状态表、真实渲染、`ui-reviewer`） |
| 构建、依赖、配置 | 受影响的解析、类型检查、构建或启动路径；生成物与配置来源一致 |
| 复杂度 / 性能相关 | 同等语义下的复杂度依据与代表性规模测量 |
| 纯文案、格式、机械修改 | diff、语法或链接检查；不写复述实现的测试 |

- 不固定覆盖率或测试数量；项目自己规定的检查必须跑。
- 并行测试使用独立数据库、端口、输出目录，冲突的检查串行。
- 汇合后在集成状态上重跑受影响检查；共享变更让旧的局部证据失效。
- 失败先归因（实现 / 环境 / 测试本身）；既有失败单独记录，不混入本次结论。

## 6. 复核

- M 档：`/code-review`，不可用时派一个 `reviewer`。L 档：多视角并行找问题，再逐条对抗验证，只处理被证实的——`dispatch.py review-args --range <检查点>..HEAD --prompts` 按改动规模和路径风险选出视角并生成各段提示（Workflow 工具可用时同一份参数交给 `/dev-spec-review`）。涉及鉴权、外部输入、敏感数据时必须包含 security 视角。
- 复核 → 修复 → 复审以一轮为限；仍有分歧时主会话读代码裁决，不让代理互相往返。
- 需要精简实现时用 `/simplify`；它只管质量不找缺陷，不能替代复核。
- 只处理有触发条件和影响的真实问题；风格偏好不当缺陷。复核后的修复改动要重跑受影响检查。

## 7. 交付：PR 与 CI

- 发 PR 前在集成状态上跑完必要检查；PR 描述列出变化、验证与限制、未验证面。推送与发 PR 按授权执行。
- 推送到已有 PR 前查看标签（`gh pr view <n> --json labels`）：带 PR Steward 标签说明另有代理在管理，不推送、不启动监控，先请用户选择。没有 `gh` 时向用户确认。
- 读 CI：桌面端发 PR 后调用 `mcp__ccd_pr__get_status`（未绑定时先 `bind_pr`）；仍在运行就去做别的事再回来读，不自建轮询。终端里用 `gh pr checks <n> --watch` 放后台。CI 失败先交 `test-triager` 归因（实现 / 环境 / 测试 / 既有），再修。Auto-fix 与 auto-merge 由用户决定（auto-merge 为 squash，且需仓库设置允许）。
- 界面改动在桌面端用 Browser 预览做真实渲染检查（项目的 `.claude/launch.json`，自动验证默认开启）；没有预览配置时先补配置再验证。
- 远程（SSH）会话：服务器往往没有 `gh`、没有显式 git 身份，端口也被长期服务占用。开工前用 `/dev-spec-dispatch` 的 `env` 看清条件；没有 `gh` 时在服务器上止于提交与推送，PR、CI 与发布由本机会话完成。
- 范围外的问题不顺手改：宿主支持 `spawn_task` 时拆成独立任务，否则在交付说明中列出。
