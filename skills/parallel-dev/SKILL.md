# 并行开发手册

前提：架构边界与共享契约已按 `dev-workflow` 确定。本手册只管"怎么安全地并行并收拢"。

## 1. 选择机制

| 情况 | 方式 |
| --- | --- |
| 小修、强依赖排障、同一文件 | 主会话串行，不委派 |
| 只需结论的大范围检索 | `Explore` 子代理（只读，可多个并行，各给不同问题） |
| 方案设计、依赖不清 | `Plan` 子代理或主会话 Plan 模式 |
| 多个独立文件组并行实现 | `implementer` 子代理 × N，每个 `isolation: "worktree"`，`run_in_background: true` |
| 文件组不相交且构建/测试无共享输出 | 也可在主工作树并行写（省去 worktree 依赖安装），但测试串行或隔离输出目录 |
| 独立复核 | `reviewer` / `security-reviewer` 并行，各给不同视角；可读同一份代码 |
| 测试失败归因 | `test-triager`（只读） |
| 成员需互相讨论、质疑、长期分端协作 | 代理团队（需 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`，仅交互会话），3–5 人起步 |
| 用户明确要求独立会话 | 新会话（`claude --worktree <name>` 或桌面端并行会话）；内部委派留在当前会话 |

代理数量按真实独立工作量与收益决定；创建失败时复用已有代理（`SendMessage`）或本地继续，不反复重试。

## 2. 派发前检查（全部满足再派写入型工作）

1. **契约检查点**：共享类型/schema/接口已写好，并在任务分支提交为本地检查点（本地检查点提交属于并行流程的一部分；推送仍需授权）。用户禁止提交时，改用主工作树内的不相交文件组并行或串行。
2. **worktree 基线**：项目 `.claude/settings.json` 设有 `"worktree": {"baseRef": "head"}`；否则 worktree 从远端默认分支创建，看不到检查点。
3. **环境**：需要的 gitignored 文件（`.env` 等）写进 `.worktreeinclude`；工作包里写明在 worktree 内安装依赖的命令。
4. **运行资源**：给每个写入者分配独立端口、数据库名/schema、缓存与输出目录；无法隔离的步骤标为串行。
5. **归属表**：每个文件组、共享文件、资源只有一个负责人；共享文件（锁文件、全局配置、迁移、公共类型）默认归主会话。

## 3. 工作包

子代理看不到主会话历史，工作包必须自包含。模板见 [references/work-package.md](references/work-package.md)。要点：目标、基线提交、负责文件（含"禁止修改"清单）、共享接口位置、运行资源、授权与禁止动作、验收命令、回报格式。

同一消息内一次性发出所有独立的 Agent 调用，使其真正并行；给每个代理起名以便后续 `SendMessage` 续接。

### Hook 强制（已安装 dev-spec 守卫时）

| 时机 | 检查 | 结果 |
| --- | --- | --- |
| 主会话派发 `isolation: "worktree"` 的 Agent | 主工作树有未提交改动；或 `worktree.baseRef` 非 head 且 HEAD 与远端默认分支不同 | ask：子代理看不到这些内容 |
| `implementer` 在 worktree 内编辑 | 未声明 `dev-spec-owner.json`；路径属于 forbidden 或不在 owned | deny |
| `implementer` 结束 | 有未提交改动；自基线无提交；基线 diff 越界（含 Bash 写入） | 阻止一次结束并要求处理；第二次放行，由回报说明 |

Hook 是防漂移的补充，集成时仍须按 §5 检查真实 diff。

## 4. 进行中

- 主会话继续做未委派的关键路径工作，用完成通知回收结果，不轮询、不重复实现。
- 子代理发现契约问题：回报给契约负责人（通常主会话），独立部分继续。负责人改契约 → 提交新检查点 → 用 `SendMessage` 通知受影响代理新的提交 SHA，由其合入后继续。
- 需求或约束变化：只更新受影响的工作包。

## 5. 集成

1. 读每个代理的回报：分支名、提交 SHA、改动文件、实际检查结果、未验证面。
2. 检查真实 diff：`git diff <检查点>..<分支> --stat`，确认没有越界修改归属外的文件；越界改动退回或由负责人重做。
3. 按依赖顺序合入任务分支（`git merge --no-ff <分支>` 或 cherry-pick），冲突出现在共享文件说明归属被破坏，先查原因再解决。
4. 在集成状态上运行受影响的完整检查（构建、类型、测试、必要的端到端）；单包通过不代表集成通过。
5. 用 `reviewer` 做集成后复核（大改动可多视角并行）。

## 6. 改派与接管

- 先确认原执行者已停止：收到完成/失败通知，或已 `TaskStop`。超时、失联、"已发停止请求"都不算停止。
- 核对遗留 diff 与运行中的进程，再把剩余工作连同现状交给新负责人；绝不双写抢进度。

## 7. 代理团队要点

- 适合：多视角研究/评审、竞争性假设排障、前后端测试分端长期协作。不适合：顺序任务、同文件编辑、强依赖。
- 在派生提示里给足上下文（队友不继承主会话历史）；每人 5–6 个自包含任务；按文件组划分避免覆盖。
- 质量门：在项目 hooks 里用 `TaskCompleted`（exit 2 拒绝完成并反馈）运行该任务的验收命令；`TeammateIdle` 用于防止过早空闲。不要用关键词判断"是否完成"。
- 限制：`/resume` 不恢复进程内队友；一个会话一个团队；队友不能再建团队。

## 8. 跨仓 / 多会话协调

仅当交付确实依赖多个仓库或既有会话时使用。

- 逐仓读取各自的 CLAUDE.md 与规则，不假定次仓规则已加载；Git 命令显式指定目录。
- 记录每个仓库的分支与被测 SHA（或包版本）、契约权威来源、生产者/消费者关系；不能只约定"各仓最新版"。
- 指定一名联合验收负责人；证据绑定参与版本组合与实际环境，单仓 CI 绿不等于整体交付。
- 向其他会话发送消息会驱动其执行：只发新事实、影响、基线和所需动作，不重复派发。

## 9. 收尾

- 停止无关的后台任务与代理；列出 `git worktree list`，已合入且无剩余改动的 worktree 与分支清理掉，保留的说明原因。
- 清理自建的临时目录、端口占用进程。
- 按 `04-git-delivery` 的完成条件与交付格式汇报。
