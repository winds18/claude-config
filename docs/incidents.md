# 事件记录

规范的每一条新增或修改都应能追溯到这里的一条事件。格式：现象 → 原因 → 修订（落点）。只记录规范本身的缺陷；项目层面的教训写入该项目的自动记忆。

## 2026-10-08 worktree 子代理无法写归属声明

- 现象：端到端测试中 implementer 用 `cat > "$(git rev-parse --git-dir)/…"` 声明归属被拒，改用字面路径同样被拒。
- 原因：Claude 的 worktree 隔离拒绝子代理执行含 `$(...)` 的命令及指向 `.git/worktrees/` 的路径。
- 修订：改为 Write 约定文件 `.dev-spec-owner.json`，由 hook 进程截获并写入私有 git 目录、锁定（`hooks/worktree-guard.py`、`agents/implementer.md`）。

## 2026-10-08 frontmatter hooks 在当前会话不生效

- 现象：同一测试中，声明前的写入没有被拒绝；直接调用守卫脚本则返回 deny。
- 原因：子代理定义在会话启动时缓存，之后添加的 frontmatter hooks 不会进入已启动的会话。
- 修订：README 注明修改 `agents/*.md` 后需新开会话；端到端验证必须在新会话进行。

## 2026-10-08 结束核验误判越界

- 现象：worktree 从晚于声明基线的 HEAD 创建时，主会话之后的提交被算作子代理的越界改动。
- 原因：以声明的 base 做 diff，而不是分支自身的创建点。
- 修订：结束核验以分支 reflog 的创建点为准，base 仅作兜底（`hooks/worktree-guard.py`）；`integrate.py` 默认用 merge-base。

## 2026-10-08 会话工作目录被切进 worktree

- 现象：排查时 `cd <worktree> && …` 使主会话的工作目录变成测试 worktree，环境随之按 worktree 隔离处理。
- 原因：Bash 的工作目录在调用之间保持；主会话进入 worktree 会改变后续所有命令的上下文。
- 修订：查看 worktree 一律用 `git -C <path>` 或绝对路径，不 `cd` 进去（`skills/parallel-dev/SKILL.md` §4 末段）。

## 2026-10-08 脱敏后的测试假值触发占位符白名单

- 现象：把测试密码改为含 "Fake" 的值后，"疑似硬编码凭证应 ask" 的测试失败。
- 原因：守卫对含 example/fake/test 等词的值视为占位符放行。
- 修订：测试用随机无语义的假值并在运行时拼接；公开仓库推送前的脱敏检查纳入 `scripts/validate.sh`（仓库内无疑似密钥）。

## 2026-10-08 集成环节缺少确定性步骤

- 现象：派发与结束都有 hook 把关，但合并、越界核对、集成验收与清理全靠手工，压缩后难以恢复状态。
- 原因：流程只规定了"做什么"，没有提供确定性工具。
- 修订：新增 `skills/parallel-dev/scripts/integrate.py`（status/plan/apply/cleanup），规则要求合并只走该脚本、恢复先运行 status。

## 2026-10-08 复核发现集成脚本与 workflow 的漏洞

- 现象：独立 reviewer 在临时仓库复现：`cleanup` 默认会删掉用户自己的 worktree 甚至 `main` 分支；把 forbidden 文件重命名进 owned 不被发现；worktree 移除后越界检查整体失效；同名 tag 干扰分支解析；`./` 前缀与目录名中间的通配符让归属重叠检查漏报；代理抛错时复核发现与实现回报被静默丢弃；测试桩与脚本依赖同一个未经验证的运行时签名假设。
- 原因：默认目标范围过宽；`git diff --name-only` 默认开启改名检测；归属只从现存 worktree 读取；测试只覆盖了作者设想的路径（"两套同假设的 mock"）。
- 修订：`integrate.py` 默认只处理 dev-spec worktree、统一用 `refs/heads/`、`--no-renames`、按分支持久化归属副本、无声明即阻塞；守卫结束核验同样 `--no-renames`；workflow 不依赖 pipeline 第二参数、失败保留为 uncertain/错误并列出 `failed_lenses`；测试新增严格运行时变体与每条复现用例。

## 2026-10-08 规则复核发现指令冲突

- 现象：L 档无条件要求 Plan 模式（与自主推进冲突）；"禁止提交时改用主工作树并行"无法执行且无 hook 约束；包数阈值三处不一致；常驻规则重复技能细节；本轮新增规则缺少依据记录。
- 原因：同一流程在常驻规则与技能中各写一份，修改时只改了一处。
- 修订：Plan 模式改为有条件；删除主工作树并行回退（禁止提交即串行）；阈值统一为"≥2 个可独立验证的包"并只写在 `03-parallel`；常驻规则只保留原则与指针，细节归 `parallel-dev`/`dev-workflow`；依据补记于本文件与 `design.md`。

## 2026-10-08 修复核验发现的残余问题

- 现象：复核者核验修复时复现：分支删除后留下的持久化归属副本会被同名新分支继承，使用户自己的 worktree 被当作 dev-spec 管理并被 cleanup 删除；`.claude/worktrees/` 下未声明的 worktree（可能是用户的并行会话）会被默认 cleanup 删除；目录缺失时执行了全局 `worktree prune`；`failed_lenses` 用了过滤后数组的下标；preflight 只比较 origin/HEAD 与 HEAD。另：git 辅助函数 `.strip()` 截掉 porcelain 首行前导空格，导致首个改动路径少一个字符，守卫会把负责范围内的文件误判为越界（真实运行时发现）。
- 原因：持久化副本缺少与分支历史的绑定；"受管"判定混用了副本与路径；输出清洗过度。
- 修订：副本记录 `declared_at` 并要求其在分支历史中；"受管"只看私有声明或路径，默认 cleanup 只处理有声明的；目录缺失时跳过；按原始下标标注失败视角；preflight 检查检查点是否在 worktree 实际起点的历史中；git 输出只去尾部换行。每项均有回归测试，且已用"恢复旧代码 → 测试失败"确认测试有效。

## 2026-10-08 并行包各自通过、集成后失败

- 现象：第三轮升级用两个 worktree implementer 并行实现（包 A 静态检查、包 B 派发技能）。两包各自全量校验通过，`integrate.py apply --verify` 在集成状态上失败：包 A 的测试为验证"技能目录也算合法引用"临时创建了 `skills/dev-spec-dispatch/`，而包 B 正好真实创建了它。
- 原因：测试夹具借用了一个真实存在（于另一包中）的名字；单包验证看不到其他包。
- 修订：测试改用专用假名；印证"验收以集成状态为准"的规则与 `apply --verify` 的必要性，无需新增规则。

## 2026-10-08 第三轮复核：派发脚本绕过提交前密钥扫描等

- 现象：两名 reviewer 在临时仓库复现：`dispatch.py prepare --commit` 在 Python 子进程内 `git add -A` 并提交，PreToolUse 守卫看不到 `git commit`，未跟踪的密钥文件进入检查点；`--changed` 只按"文件 → 自身测试"映射，改 `integrate.py`、`global/`、`agents/` 时漏跑消费它们的 dispatch/install/self_update/validate 测试，出现"增量通过、全量失败"；Markdown 计划不识别代码段与 ASCII 逗号、未转义 `|` 让列错位、`case_design` 被静默丢弃；security 视角只看路径子串（漏判内容层面的鉴权改动、误判 React hooks）；映射测试把不完整的映射写成了期望值。
- 原因：hook 只拦截直接工具调用，脚本内的副作用需要自己守门；依赖映射靠手写清单。
- 修订：脚本内提交前复用守卫检测器扫描暂存内容（找不到守卫即拒绝）、失败恢复原暂存区；映射按"生产者 → 全部消费者"列出，并新增从测试代码推导依赖的检查；Markdown 解析识别代码段并校验列数；未知顶层字段报错；视角按路径词与新增代码内容判断并给出 notes；新增 Python 产出直接交给 workflow 真实校验的跨语言契约测试。所有修复均用"恢复旧代码 → 测试失败"确认有效。

## 2026-10-10 新会话端到端验证：流程对琐碎任务用力过猛

- 现象：在全新会话里用两个"输出 hello 的两行脚本"包验证三阶段流程。结果正确，但每个 implementer 耗 7 万余 token、包级复核两轮、测试写到 39–59 行并断言 shebang 写法、可执行位与 stderr 换行；Workflow 工具在桌面会话不可用，主会话只能读 workflow 脚本来手动模拟三阶段；implementer 的二十多条 `bash …` 命令被 Claude 的 worktree 隔离拒绝后自行摸索出直接执行的写法；验证会话在集成后停住，未清理也未写报告。
- 原因：用例设计与复核没有"与规模相称"的约束；手动回退路径只写了派 implementer，没写三阶段；隔离对命令形态的限制没有告知实现者。
- 修订：case-designer、reviewer、implementer 与包级复核提示加入相称性约束；`effort: "low"` 的包跳过用例设计；parallel-dev 写明手动三阶段；implementer 说明被隔离拒绝时的处理办法。同时证实：SessionStart 自动更新检查、子代理加载、归属 hook 在真实新会话中均生效。

## 2026-10-10 核心规则两节被脚本替换误删并随三个版本发布

- 现象：`01-core.md` 的"上下文经济"与"授权与安全"两节自第二轮升级（65ac1e7）起消失，v1.0.0–v1.1.1 均不含。两轮独立复核、交叉引用检查与 CI 都没有发现。
- 原因：一次脚本编辑用"从某行到文件末尾"作为被替换文本，把其后的两节一并替换掉；所有检查都在验证"引用是否有效"，没有任何检查验证"应有的内容是否还在"。
- 修订：恢复两节；新增静态检查：常驻规则的章节清单是受版本管理的事实，章节消失必须同时修改清单才能通过（防止无意删除）。并已对全部规则、技能、子代理文件做历史标题比对，确认只此一处。

## 2026-10-10 首次真机部署到 Debian 服务器

- 现象：对一台 Debian 13 服务器（无 node、无 `~/.claude`）执行 `install.sh remote`：安装、从 v1.1.1 升级到 v1.2.0（旧更新器在无 node 环境跑候选的全量校验）、守卫拦截均成功。同时暴露：服务器没有显式 git 身份、没有 `gh`、已有多个端口被占用，规范的交付与资源分配步骤默认了本机条件；新写的 `dispatch.py env` 在 macOS 上因 `lsof` 输出含非 UTF-8 字节而崩溃；用 `git var GIT_AUTHOR_IDENT` 判断身份会把 git 自动拼出的"用户名@主机名"当成已设置。
- 原因：此前所有验证都在开发机上完成；身份判断沿用了"命令成功即有身份"的假设。
- 修订：`preflight` 与 `env` 只认显式配置的 `user.name` / `user.email`；`env` 列出 gh、node、docker、监听端口并容忍非 UTF-8 输出；dev-workflow 写明远程会话止于提交与推送。

## 2026-10-10 放宽发布闸门时的安全复核

- 现象：为省去合入后重复等待 CI，让发布闸门采用"文件树相同的被合并提交"的 CI 结果。安全复核复现：合并提交 CI 失败后点重跑，重跑期间状态变回"进行中"即可放行；`main` 上某提交被 revert 后合入未更新的分支，文件树相同但 PR 上验证的是另一棵树；分支上缺少或跳过的检查被当成已验证；三处关键条件被改动后测试仍全绿。
- 原因：只按"当前状态"判断，没有看历史轮次与分支是否包含合并时的主干。
- 修订：回退路径要求——合并提交任何一轮都未失败、分支已包含合并时的 main、分支上每项检查都成功并覆盖合并提交上的全部检查名；补 9 项测试，四种变异全部被抓到。

## 2026-10-11 界面规范的首次真实验证

- 现象：用一个典型的"生成味"页面验证新加的界面规范。`ui_lint` 报出 19 条可客观检出的问题；按 `ui-reviewer` 定义行事的子代理用浏览器在 1280 与 375 两种视口截图并走了键盘流程，发现脚本查不出的交互阻断（空提交与非法输入都被当作成功、回车无反应、键盘走不通主任务）。同时暴露：浏览器对本地文件只做静态快照，必须有预览服务才能交互；定义文件没说遇到原生 `alert` 卡住工具时能否在页面内打桩、深色模式如何切换、造不出的状态如何回报、截图如何交付。`ui_lint` 首版在真实项目上约三分之二是误报。
- 原因：规则写的时候没有在真实页面与真实项目上跑过。
- 修订：`ui-reviewer` 写明页面内的临时调试操作不算改文件、深色模式的两种切法、造不出的状态列为"未能制造"、截图不落盘；`ui_lint` 跳过测试文件、注释、自定义组件、弹窗遮罩与数据里的 emoji，并对不存在的路径报错。


## 2026-10-11 审计：唯一可用的路径却写得最薄

- 现象：Workflow 工具在桌面端会话不可用，手动三阶段是实际唯一能走的路径；但用例设计、实现、包级复核与集成后复核的提示内容只存在于 workflow 源码里，技能里只有三行概述，工作包模板也没有"先写成测试的场景"与完成状态。另有：L 档的触发条件过宽（任何契约变化）、读 CI 与查 PR 标签在没有 `gh` 时无路可走、`/code-review` 不可用时没有替代、复审没有轮次上限、完成条件在技能与常驻规则里各写了一遍。
- 原因：规范按"workflow 可用"来写，后来才确认它在目标环境里不可用，文字没有跟着翻过来。
- 修订：`dispatch.py prompts` 与 `review-args --prompts` 生成全部提示，测试保证关键句与 workflow 逐字一致；技能与常驻规则改为手动路径为主、workflow 可选；L 档改为"波及 2 个以上消费者或模块"；补上无 `gh`、无 `/code-review` 时的做法与复审一轮为限；删去重复的完成条件。
